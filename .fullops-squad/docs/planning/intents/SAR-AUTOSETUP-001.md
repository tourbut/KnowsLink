# SAR-AUTOSETUP-001 — Claude Code·Codex 사용자가 명령 하나와 필수 확인만으로 첫 메시지를 보낸다

과제 2개 이상(designer 설계, dev 설치기·화면, tester 큰 틀 검수)에 걸치는 묶음 작업의 의도다. 사용자가 승인하면 `status`를 `approved`로 바꾸고 `## 승인`에 근거를 적는다.

## 배경

- 2026-10-22 사용자 결정 D027로 C-01 Codex 세션 수신 다음 과제가 C-03 클라이언트 자동 설정이다. C-03의 대상은 Claude Code와 C-01 뒤의 Codex다. 키 복사·자격 공유·소유자 동의 없는 연결을 금지한다([SAR-COMPETE-001 C-03](../product-specs/SAR-COMPETE-001.md#후보-표)).
- 이슈 #9의 주요 비교점은 경쟁 서비스의 10종 넘는 클라이언트 자동 설정이다. KnowsLink는 클라이언트 수로 경쟁하지 않는다(NG-05). 검증한 두 호스트의 설치 마찰을 줄인다.
- C-01 Codex 세션 수신은 main에 병합됐다. 근거는 [Codex DEV 보고](../../evaluations/qa-reports/SAR-CODEX-RECV-001-DEV-test/report.md)와 [D11 Codex 절](../../operations/user-guide.md#codex-세션에서-사용하기--sar-codex-recv-001-docs)이다.
- 현재 설치는 사용자가 [adapters 설치 문서](../../../../adapters/README.md#호스트별-설치--sar-sse-install-001)의 명령을 단계별로 직접 실행한다. 회원 화면 '어디에서 사용할까요?'는 Codex를 '지원 확인이 필요한 호스트'로 두고 설치 명령을 보이지 않는다([U8](../../design-docs/SAR-UX-ISSUES-002.md#어디에서-사용할까요-선택지)).

## 문제

Claude Code나 Codex를 쓰는 새 회원은 친구 메시지를 받기 전에 개발자용 절차를 직접 따라야 한다. 다음 표는 2026-10-22 문서 기준의 현재 절차다. 실제 소요 시간은 측정하지 않았다. DEV가 착수 때 깨끗한 Windows 11에서 실측해 기준선으로 남긴다.

| 단계 | Claude Code | Codex |
|---|---|---|
| 1 | 새 폴더에 저장소 clone·고정 SHA checkout | 같음 |
| 2 | 의존성 설치·빌드 | 같음 |
| 3 | Node `22.22.2` 선택 | 같음 |
| 4 | `package_plugin.py --host claude --install-dir <새 절대경로> --connect --verify` | `--host codex`로 같음 |
| 5 | `/plugin marketplace add <절대경로>`·`/plugin install knowslink@knowslink-plugins` | `CODEX_HOME` 준비, `codex plugin marketplace add <절대경로>`, `codex plugin add …` |
| 6 | 세션에서 `knowslink_connect` 요청·허가 | 같음 |
| 7 | 브라우저 Google 로그인·지문 비교·이름·동의 | 같음 |
| 8 | `knowslink_connect_status` 확인 | 같음 |
| 9 | `/knowslink-session on` | 승인 모드 확인, `knowslink_session` `on`, Codex 도구 승인, 4자리 코드 |

- 사람이 직접 입력하는 절대 경로가 2번 이상이다. 셸 명령은 5개 이상이다.
- 이미 설치한 사람이 같은 절차를 다시 따르면 새 폴더·새 agent가 생긴다. 기존 설치를 갱신하는 안내가 없다.
- 실패하면 어느 단계에서 무엇이 바뀌었는지 알 수 없다. 사용자가 폴더를 지우거나 새 경로로 다시 시작한다.

## 바라는 결과

- 회원 화면에서 Claude Code 또는 Codex를 고르면 그 컴퓨터에서 실행할 명령 하나가 보인다.
- 사용자는 명령 하나를 실행한다. 사람이 확인해야 하는 단계만 직접 한다. 확인 단계는 설치 계획 동의, 브라우저의 Google 로그인·지문 확인·이름·동의, 세션 연결, 발송마다의 승인이다.
- 같은 명령을 다시 실행하면 기존 설치를 갱신한다. 기존 agent·키·친구는 그대로다.
- 실패하면 실패한 단계, 이미 바뀐 것, 다음 행동이 보인다. 같은 명령을 다시 실행하면 이어서 진행한다.
- 서명·승인·키 경계는 지금과 같다. 자동 설정은 사람 확인 단계를 줄이지 않는다.

## 성공 기준

큰 틀 검수는 이 기준으로 판정한다. 측정 환경은 깨끗한 Windows 11, 호스트 설치·로그인 완료, KnowsLink 회원 로그인·이름 설정 완료, 친구 수락 완료 상태다. `확인할 흐름`의 ID는 [D02 SAR-AUTOSETUP-001](../product-specs/SAR-AUTOSETUP-001.md)의 수락 기준이다.

## 대상 사용자와 주요 흐름

대상: 자기 컴퓨터에서 Claude Code 또는 Codex를 쓰는 KnowsLink 회원이다. 개발자일 필요는 없지만 터미널에 명령 하나를 붙여 넣을 수 있다.

신규 흐름:

1. 회원 화면 '어디에서 사용할까요?'에서 'Claude Code 작업 세션' 또는 'Codex 작업 세션'과 '처음 연결'을 고른다.
2. 화면에 보이는 명령 한 줄을 복사해 그 컴퓨터의 터미널에서 실행한다.
3. 설치기가 설치 계획(설치 폴더, 바꿀 호스트 설정, 만들 agent 폴더)을 보인다. 사용자가 동의한다.
4. 설치기가 내려받기·검증·설치·호스트 등록을 한다.
5. 설치기가 Google 연결 링크를 연다. 사용자가 자기 브라우저에서 로그인하고 터미널의 지문과 화면의 지문을 비교한다. 에이전트 이름을 정하고 동의한다.
6. 설치기가 키 저장을 확인하고 다음 행동을 보인다. 호스트 재시작이 필요하면 이때 알린다.
7. 사용자가 작업 세션에서 세션을 연결한다. Claude Code는 `/knowslink-session on`, Codex는 `knowslink_session` `on`과 Codex 도구 승인·4자리 코드다.
8. 사용자가 친구에게 보낼 메시지를 요청하고 발송 승인 대화상자에서 승인한다.

기존 흐름: '기존 연결 계속'을 고르면 같은 명령이 보인다. 설치기가 기존 설치를 찾아 갱신 계획을 보인다. Google 연결과 이름 단계는 건너뛴다. 세션 연결은 호스트 재시작 뒤 다시 한다.

## 제약과 범위 밖

제약:

- LG-04: 키 복사·재등록을 권하지 않는다. 신규 설치와 기존 갱신을 구분한다.
- HP-10·SP-05·SP-06: 발송마다 소유자 승인. 자동 답장 0. 설치 완료를 발송 승인으로 쓰지 않는다.
- SP-01·SP-02: 설치만으로 세션이 수신하지 않는다. 세션 연결은 소유자가 명시적으로 한다. 한 agent는 한 세션만 받는다.
- SP-12·NG-05: 실측 근거가 있는 호스트·버전·OS만 지원 문구에 쓴다. 현재 근거는 Claude Code `2.1.302`·Codex CLI `0.163.0`·Windows 11이며 격리 합성 서버 기준이다.
- 자격 복사 금지: 다른 설치·Grok·Dots·다른 호스트의 키와 credential, 호스트 인증 파일을 읽거나 복사하지 않는다.
- Google 동의·지문 비교·에이전트 이름은 사람이 자기 브라우저에서 한다. 자동화하지 않는다.
- Codex 승인 모드(`approval_policy`)와 YOLO 설정을 설치기가 바꾸지 않는다. 확인하고 안내만 한다.

범위 밖:

- Claude Desktop, Grok CLI, Cursor, Hermes Agent, 그 밖의 호스트의 자동 설정(NG-05).
- Grok Bot installer와 Dots Remote MCP 연결 흐름의 변경.
- macOS·Linux 지원 표기. Q4 결정 전에는 Windows 11만 지원 문구에 쓴다.
- 친구 요청·수락의 자동화, 설치 직후 자동 시험 발송.
- 설치 제거 명령. 이번에는 제거 방법 안내만 출력한다. 키 철회는 기존 웹 화면을 쓴다.
- 공개 marketplace 등록.

## 열린 질문

승인 전에 사용자가 답한다. 담당은 사용자, 정리는 designer다. 답에 따라 D02·D04·DEV 지시서를 고친다.

| ID | 질문 | 선택지 | 추천 | 영향 |
|---|---|---|---|---|
| Q1 | 명령을 어떤 형태로 배포하는가? | A. 한 줄 다운로드·실행. 명령에 고정 버전이 있고 설치기가 내용물 checksum을 검증한다. / B. 설치 파일을 내려받은 뒤 실행하는 두 줄. / C. 지금처럼 저장소 clone·고정 SHA·스크립트(Grok 방식). | A | A는 S1의 '셸 명령 1개'를 만족한다. 파이프 실행의 신뢰는 KnowsLink 도메인 HTTPS와 고정 버전·checksum에 기댄다. B는 사람 행동이 1개 늘지만 실행 전 파일을 볼 수 있다. C는 git·빌드 도구가 필요해 S1·S3를 만족하기 어렵다. |
| Q2 | Google 연결을 어디서 시작하는가? | A. 설치기가 설치 직후 연결 링크를 열고 지문을 터미널에 보인다. / B. 지금처럼 호스트 세션에서 `knowslink_connect`를 요청한다. | A | A는 호스트 재시작 전에 연결을 끝내 행동 수가 2개 준다. B는 호스트 도구 discovery가 먼저 되어야 하고 행동이 늘어난다. 두 경우 모두 지문 비교·동의는 사람이 한다. |
| Q3 | 호스트 등록 범위는? | A. 사용자 기본 설정에 KnowsLink 항목만 등록하고 설치 계획에서 동의를 받는다. / B. 세션 한정(`--plugin-dir`, 별도 `CODEX_HOME`)만 쓴다. | A | A는 매번 경로를 넣지 않아도 된다. 다른 MCP 항목과 인증 파일은 건드리지 않는다(S4). B는 사용할 때마다 경로를 넣어야 해 S1을 만족하지 못한다. |
