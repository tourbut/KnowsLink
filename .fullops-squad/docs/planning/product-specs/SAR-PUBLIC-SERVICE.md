# KnowsLink 일반 이메일 서비스 수락 기준

## 결정 근거와 현재 상태

사용자 원문은 “일반서비스가 가능한 수준까지 하고 openai dots 연결하는거야.”다. 대상 dot 이름은 “다닷”이며 Grok Bot 표시 이름은 “노우”다. 표시 이름은 내부 고유 agentID와 구분한다. 최신 사용자 원문은 “내가 운영버전 테스트할꺼는 grok bot 과 openai dots를 연결해서 테스트하는거야 둘다 내 이메일로 가입할꺼야.”다. 최종 운영 E2E는 동일 일반 이메일의 공식 xAI Grok Bot “노우”↔다닷이다. SAR-PUBLIC-SERVICE-001은 이 지시를 일반 이메일 신원과 실제 에이전트 메시지 서비스의 새 제품 범위로 반영한다. 일반 사용자는 자기 에이전트의 owner다. 운영 관리자는 별도 권한이다. 연락처는 계속 에이전트이며 장기 채팅 제품으로 전환하지 않는다.

기준은 `6c0d132d26dac22693f1c1ffb986fc4f61bdbd09`이며 준비 HEAD는 `608fe06cf0d67d97a483bd088d9834c34049fb6f`다. 현재 `/v1/owners`는 이메일 확인 없는 합성 가입이다. `link.knowslog.com`의 owner-only Access와 시험 Service Auth는 일반 회원 인증이 아니다. [실제 Grok 시험](../../exec-plans/phases/SAR-MVP-003-ACTUAL-TRIAL.md)은 수동 CLI 왕복 성공만 증명한다. [시험 종료](../../exec-plans/phases/SAR-MVP-003-TRIAL-CLEANUP.md)의 삭제와 owner 보호 복귀는 유지한다. 이 문서 작성 시 일반 서비스 구현·공개 수락과 다닷 연결은 미완료다.

일반 서비스는 누구나 같은 조건으로 이메일 가입을 시작할 수 있다. 사전 명단이나 서비스 가입 초대를 요구하지 않는다. 에이전트 사이의 첫 관계에는 수신 owner의 명시적 수락이 필요하다. 기존 [MVP 요구사항](SAR-MVP.md)의 C1–C5와 frozen `relay.v1`은 계속 적용한다. 이번 요구와 충돌하는 이전 실벤더 제외·어댑터 순서는 아래 새 우선순위가 대체한다. 실일정 공개·결제·임의 업무 외부 발송·유료화의 held는 유지한다.

## 운영 조사 근거 반영

OPS의 `0313deae0dec9af813b70ee9685e1a6d0a2b84d7`에서 `SAR-PUBLIC-SERVICE-OPS-READINESS.md`를 `git show`로 읽었다. 해당 결과는 coor가 통합할 자료이며 진행 designer 체크아웃에 merge하지 않았다. 기록 경로는 통합 후 `docs/exec-plans/phases/SAR-PUBLIC-SERVICE-OPS-READINESS.md`다.

조사 시점에는 relay가 Access JWT/이메일을 읽지 않고 Basic/Bearer 합성 신원만 읽었다. root 정책은 관리 이메일 하나만 허용했다. managed OAuth는 꺼져 있고 trial token은 없었다. IdP/조직/좌석·DNS/WAF 일부는 권한 부족으로 미확인이다. 따라서 단순 root everyone 변경은 PS-01/04를 충족하지 못한다. 일반 회원 신원 바인딩과 비브라우저 agent 인증 경계를 먼저 구현·검증한다. 일반 사용자의 Cloudflare 계정 가입을 필수로 요구하지 않는다. 신원 제공자·Access/직접 인증·MCP 연결 선택은 DEV/OPS의 기술 책임이다.

서버의 4코어·가용 RAM 6002 MiB/총 13906 MiB·swap 약 99%·디스크 가용 312GB는 한 시점 관측이다. PSI는 관측 시 0이었다. 업무 상태는 단일 jsonb 행이고 처리량은 미측정이다. 현재 낮은 사용량으로 회원 100명·agent 200개를 안전 수용한다고 보장하지 않는다. 새 기본값 이하의 정상 polling·수용량/보존 기록 포화·경합·재시작·안전 종료를 DEV가 검사한다. OPS는 공유 서비스 보호와 자원 근거를 확인한 뒤 공개한다.

현재 자동 백업과 별도 저장소는 없고 최신 dump 복원은 이번 조사에서 미검증이다. 아래 RPO 24h/RTO 4h·일일 백업·7일 보존·암호화는 새 제품 결정이며 현재 충족 상태가 아니다. OPS는 live 디스크 장애에 대비한 별도 디스크 또는 호스트의 사본과 복원 근거를 마련한다. 신규 비용·권한은 필요한 항목만 coor가 사용자에게 연결한다.

### PS-07 관계 초대의 반복과 재수락

2026-10-06 SAR-PUBLIC-AGENTS-001-POLICY에서 원본 AGENTS 리뷰 L2의 제품 해석을 확정한다. 아래 규칙은 PS-07과 PS-11의 해석이며 과거 구현의 준수 판정이 아니다.

- 같은 두 agent 사이에 유효한 pending이 있으면 같은 방향의 반복 초대는 기존 pending만 유지한다. 새 초대·세대·pending slot을 만들거나 기존 24h 기한을 연장하지 않는다. 반대 방향 초대도 별도 pending이나 자동 수락을 만들지 않는다. 현재 초대의 수신 owner가 명시적으로 결정한다.
- 이미 active이면 반복 초대는 현재 관계를 유지한다. 새 pending·active slot·세대 또는 추가 권한을 만들지 않는다.
- 거절은 현재 초대를 종료한다. 만료는 pending의 24h 기한이 끝난 상태다. 어느 쪽 owner의 철회도 현재 관계 또는 pending을 종료한다. 종료된 초대는 수락할 수 없으며 종료 상태에서는 메시지를 허용하지 않는다.
- 거절·만료·어느 쪽 철회 뒤에는 현재 유효한 agent 사이의 새로운 수동 초대를 허용한다. 거절·철회를 영구 차단으로 해석하지 않는다. 기존 한도를 모두 만족해야 새 pending을 만든다. 새 초대의 수신 owner가 다시 명시적으로 수락하기 전에는 메시지를 거부한다. 같은 owner의 두 agent도 이 조건을 지킨다.
- 재초대·재수락은 이전 종료 관계와 구별되는 새 관계 세대를 사용한다. 종료된 세대를 되살리거나 옛 수락·승인·메시지 권한을 새 세대에 재사용하지 않는다. 세대를 발급하는 시점과 기술 저장 방식은 DEV가 정한다. 재초대 자체는 전달 권한이 아니다.
- 자동 재초대·타이머 재시도·재로그인에 의한 관계 복구는 허용하지 않는다. 기존 원천의 `Auto reinvite = current active pair only`는 현재 active 관계 안의 반복에 한정한다. 거절·만료·철회 뒤 수동 재초대는 최신 일반 서비스의 이 절을 따른다. frozen의 현재 권한 재검사와 새 세대 조건은 유지한다.

새 차단 기능·쿨다운·수신 pending 한도는 이번 범위에 추가하지 않는다. 기존 owner 송신 pending 10개·전체 pending 200개·인증 principal 신규 40회/rolling 60s와 나머지 PS-11 한도를 유지한다. 반복·실패·거부도 rate에 집계한다. pending은 active slot을 소비하지 않으며 거절·철회는 안전 정리 budget을 사용한다. 이 한도는 수신 owner의 반복 노출을 없애는 보장이 아니다. 공개 전 남용 방어·자원 보호 검증은 계속 필요하다. 실제 남용이나 보호 실패가 확인되면 coor가 designer에 근거를 전달해 별도 제품 변경을 판단한다.

DEV 자동 검사와 독립 TESTER는 [POLICY 관찰 조건](../../exec-plans/phases/SAR-PUBLIC-AGENTS-001-POLICY.md#devqa-관찰-조건)을 따른다. 화면의 상태·다음 동작은 [UX-05](../../design-docs/mockups/SAR-PUBLIC-SERVICE-UX.md#ux-05-반복-초대와-재초대)를 따른다.

### PS-05/06/11 기록 보호에 따른 교체와 목록 정리

2026-10-06 coordinator의 같은 과제 추가 지시로 사용자 조건을 확정한다. DEV-FIX `4a1b80aec8fa6a06144d51f3a5609927a2644928`의 owner agent 기록 10개·agent 키 기록 20개는 기술 자원 보호값이다. 이 값은 새 상품 quota가 아니다. 활성 agent 5개·활성 키 3개 등의 기존 제품 한도는 그대로 적용한다. 기술 보호값·저장·정리 방법은 DEV 소유이고 실제 DB/CPU·복원 보호의 측정은 OPS 후속이다. 아래 조건은 구현·독립 검증 PASS를 소급 선언하지 않는다.

- 기록 보호로 새 생성·연결이 거부되면 기존 연결과 현재 권한을 임의 철회하지 않는다. 화면은 새 생성/연결 실패를 명시하고 기존 에이전트 관리로 돌아갈 수 있게 한다. 실패를 완료나 활성화로 표시하지 않는다.
- 살아 있는 agent의 키 기록이 포화하면 철회 키를 삭제하거나 같은 `kid`를 재할당해 제한을 우회하지 않는다. 해당 agent에서 키를 철회하거나 시간만 기다리는 것으로 새 키 기록 공간이 생긴다고 안내하지 않는다. 새로운 agent로 교체하는 동작을 안내한다. 기존 활성 자격은 사용자가 철회하기 전까지 현재 권한 규칙대로 처리한다.
- 교체는 새 agent의 별도 식별자·정상 연결과 owner 확인을 요구한다. 이름이 같아도 이전 agent·키·관계·승인·receipt 권한을 승계하지 않는다. 새 agent와 각 상대 사이에는 첫 초대와 수신 owner의 명시적 수락이 필요하다. 교체 중 새 관계가 대기이면 해당 메시지는 거부한다.
- 교체에 활성 또는 기록 여유가 없으면 새 연결 성공을 약속하지 않는다. 사용자는 불필요한 기존 agent를 명시적으로 철회할 수 있다. 화면은 철회가 해당 키와 관계를 종료함을 알린다. 활성 한도만 포화한 경우 철회로 활성 slot이 해제되지만 보존 기록 slot까지 즉시 해제되는 것은 아니다.
- owner의 agent 기록이 포화하면 철회·취소·거절·관계 철회는 계속 가능하다. 모든 작업은 기존 정리 budget과 현재 권한을 지킨다. 철회된 agent의 최소 24h 보존과 실제 정리 뒤 신규 생성을 수동 재시도하도록 안내한다. 반복 철회나 재로그인은 보존 기간을 줄이지 않는다. 정확히 24h에 공간이 생긴다고 약속하지 않는다.
- 철회 agent는 보존 중 철회 상태로 구분한다. 최소 24h 뒤 실제 정리가 완료되면 자기 홈 목록에서 사라질 수 있음을 안내한다. 목록에서 사라짐은 철회된 권한의 복구·일시 오류·영구 개인정보 삭제 또는 백업 삭제를 뜻하지 않는다. 새 agent 재연결과 새 관계 수락 없이는 사용할 수 없다. 보존 중인 최소 24h 기록과 C1의 살아 있는 agent `kid` 영구 재할당 금지는 유지한다.

사용자 상태·다음 동작은 [UX-04/05 교체 조건](../../design-docs/mockups/SAR-PUBLIC-SERVICE-UX.md#ux-0405-기록-포화와-agent-교체)을 따른다. DEV/QA의 포화·교체·보존·목록 관찰 조건은 [추가 인계](../../exec-plans/phases/SAR-PUBLIC-AGENTS-001-POLICY.md#기록-보호의-추가-제품-답과-관찰-조건)에 있다.

### 실제 메시지의 범위

PS-08의 첫 왕복은 사용자가 명시적으로 보낸 비민감 연결 확인 text와 관련 답장이다. text는 UTF-8 4096 bytes 이하이며 TTL은 180s다. 첨부·링크 자동 열기·도구 실행·임의 업무 외부 발송은 포함하지 않는다. 답장도 해당 agent owner의 명시적 실행 또는 해당 메시지에 한정한 승인으로 보낸다. 관계 수락을 무제한 외부 발송 승인으로 해석하지 않는다.

DEV는 기존 시험 text 계약을 일반 회원용으로 분리하거나 승격할 방법을 정한다. 시험 자격·allowlist를 일반 회원 인증으로 재사용하지 않는다. 이 text 경로는 frozen 업무 `relay.v1`과 구분한다. 업무 봉투에 canonical `body.text`나 새 wire 필드를 임의 추가하지 않는다. text에도 현재 회원/agent/키/관계 인가, 짧은 보존, 멱등, 크기 제한과 실패 표시를 적용한다. 장기 채팅 타임라인과 대화 composer는 만들지 않는다. 지원되는 실제 클라이언트의 송수신 도구와 연결 확인 화면으로 검증한다.

CPU·RAM·디스크·DB·보존 중인 철회/가입 기록의 실제 상한과 경보는 OPS의 기술 책임이다. 보호값의 존재·포화 시 새 수락 중지·기존 공유 서비스 보존을 공개 전 증명한다. 제품 문서가 임의 하드웨어 수치를 지정하지 않는다.

## 개인정보와 운영 완료 조건

미확인 이메일은 확인 수단의 최대 10분과 남용 방어 집계에 필요한 최소 기간만 보존한다. 검증 이메일과 회원 매핑은 활성 계정의 로그인에만 사용한다. 이메일을 agent 식별자·contacts·공개 receipt·Git·지원 로그에 넣지 않는다. 민감정보 없는 계정 식별자로 검증을 기록한다. 이메일 변경과 별도 관리자 대리 복구는 첫 서비스 범위에 넣지 않는다. 이메일 접근을 잃으면 자동 계정 탈취성 이전을 허용하지 않는다.

회원은 모든 세션 종료와 자기 계정 비활성화를 요청할 수 있다. 비활성화는 모든 세션·agent 자격·키·pair를 철회하고 미완료 작업을 안전 종료한다. 재로그인만으로 철회 관계를 복구하지 않는다. 영구 삭제 요청은 운영 절차로 접수하고 보존 범위를 안내한다. 비활성 계정 매핑과 민감정보 없는 보안 진단 기록은 최대 30일 뒤 정리한다. 필수 revoke metadata는 frozen 최소 24h를 충족한다. 실메시지 원문은 만료 또는 전달/응답 완료 뒤 지우고 receipt·멱등은 24h만 보존한다. 감사/진단에는 본문·인증값·개인키를 남기지 않는다.

초기 운영 복구 목표는 RPO 24h 이하, RTO 4h 이하다. 최신 사본은 live DB 디스크와 별도 디스크 또는 호스트에 보존한다. OPS는 일 1회 이상 성공 백업과 격리 복원 훈련을 근거로 검증한다. 백업은 암호화·접근 제한하고 최대 7일 보관한다. 백업/WAL 삭제가 즉시 완전 삭제라는 약속을 하지 않는다. 복원 전에 만료 메시지를 제거하고 복원된 세션·연결 자격·키·pair가 철회 권한을 되살리지 않도록 확인한다. 철회 이후 상태가 증명되지 않으면 재인증·재연결·재수락 전 전달을 차단한다.

사용자에게 제한·장애·메일 발송 실패·연결 오프라인·만료·복구 중 상태와 가능한 다음 동작을 보여준다. 오류에 내부 경로·stack trace·타 회원 존재를 노출하지 않는다. OPS는 상태 확인·민감정보 없는 지원 접수·새 수락 중지·rollback·계정 철회 절차를 D12/D13에 남긴다. 신규 수락 중지와 안전 정리는 분리한다.

DEV는 각 기능의 기술 계획·구현·자동 검사·관련 회귀와 D03/D05–D10을 같은 과제에서 완료한다. TESTER는 안정된 후보를 독립 검증한다. reviewer는 구현자와 다른 별도 세션에서 깨끗한 read-only detached fixed-SHA snapshot을 검토한다. designer는 같은 후보의 [화면 수락 항목](../../design-docs/mockups/SAR-PUBLIC-SERVICE-UX.md)을 직접 확인한다. OPS는 수락된 공개 후보에서 기존 관리 오너·공유 서비스와 실제 외부 로그인/agent 경계를 확인한다. 기존 owner 보호를 단순 해제해서 일반 가입을 노출하지 않는다.

기능별 수락과 전체 일반 서비스 수락은 분리한다. UI 사람 확인은 일반 이메일 회원의 실제 로그인·로그아웃·재로그인으로 수행한다. 자동 로그인 fixture를 사람 검수로 기록하지 않는다. 제공된 사용자 이메일이 아직 없으면 허가된 QA 환경으로 독립 검사하고 사용자의 직접 확인만 대기로 남긴다. 사용자에게 두 다른 이메일이나 두 인간 계정을 요구하지 않는다. 타 회원 음성 QA에는 독립 fixture를 사용할 수 있다. 인증값은 private form 또는 로컬 비공개 수단으로만 취급한다.

## 다닷 공식 근거와 후속 확인

2026-10-05 [Meet dots](https://learn.chatgpt.com/docs/dots)와 [Computers and apps](https://learn.chatgpt.com/docs/dots/computers-and-apps)를 직접 열었다. dot은 클라우드 컴퓨터를 사용하며 계정에서 지원·설치·활성화한 플러그인을 사용할 수 있다. 사용자 컴퓨터는 dot 프로필에서 별도로 연결한다. 로컬 사용 시 컴퓨터 온라인과 ChatGPT 앱 실행이 필요하다. 메시징 채널 연결은 앱 권한 연결과 별개다. 이 안내는 다닷 계정의 KnowsLink 설치 가능성을 증명하지 않는다.

[Plugin authentication](https://developers.openai.com/plugins/build/auth)을 직접 확인했다. 사용자별 데이터와 쓰기 도구의 원격 MCP에는 OAuth 2.1·PKCE·발견 메타데이터와 매 요청 token 검증 계약이 안내돼 있다. 공식 문서는 기존 검증된 IdP 사용을 권장한다. DEV는 일반 이메일 신원과 향후 다닷 연결의 동일 회원 매핑·최소 권한·철회 가능성을 함께 고려한다. 이 문서는 IdP·API·DB·MCP 구현을 선택하지 않는다. 계정 연결 동의는 메시지 발송·owner approve의 포괄 동의가 아니다.

[MCP Events](https://developers.openai.com/plugins/build/mcp-events)는 dots에서 이벤트 구독을 시험할 수 있다고 안내한다. 문서의 계약은 MCP 2.0 `2026-07-28`, 별도 구독·webhook 전달·callback 검증이다. 실제 계정 지원·구독·이벤트 도착과 요청 동작은 별도 검증 대상이다. 현재 relay optional webhook OFF는 유지한다. 후속 이벤트 범위 결정 없이 자동 wake를 추가하지 않는다. 문서상 기능을 공식 범용 dot inbound API로 해석하지 않는다.

후속 DEV/OPS는 다음 항목을 실제 다닷에서 확인한다.

1. 사용자 계정에서 다닷 프로필과 앱/플러그인 설치·연결 화면의 존재를 확인한다.
2. 지원되는 KnowsLink 플러그인 경로나 별도 허가한 컴퓨터 경로를 확인한다. 계정·도구·실행 위치·필요 권한을 기록한다.
3. 사용자의 같은 일반 이메일로 Grok Bot과 다닷을 각각 연결한다. 별도 agent 식별자·키·credential과 자기 agent만 허용하는지 검증한다. 재연결·만료·철회·타 회원 접근 차단을 확인한다.
4. Grok Bot의 실제 송신 ID와 다닷의 실제 수신 ID를 대조한다. 다닷의 관련 답장 ID와 Grok Bot의 실제 수신 ID도 대조한다. Codex나 로컬 B 대역 송신으로 대체하지 않는다. 수동 호출이면 그대로 표시한다.
5. 이벤트 wake를 요청하면 별도 과제를 만든다. 지원 계약·구독 수명·중복·철회·수신 및 승인 경계를 검증한다.

사용자만 제공할 입력은 일반 이메일의 실제 확인, 다닷 계정의 접근과 연결 동의, 새 비용/결제 또는 보류된 실데이터 업무의 별도 승인이다. 화면과 계정 접근 대기는 일반 서비스의 독립 구현을 막지 않는다. 숫자·기능 순서·기술 선택은 해당 담당자가 처리한다.

## 개정 이력

- 2026-10-05: SAR-PUBLIC-SERVICE-001에서 일반 신원·실제 메시지·운영 기본값과 일반 서비스 수락 후 다닷 연결 순서를 새로 결정했다. 과거 제안 승인과 시험 결과는 소급 변경하지 않았다.
