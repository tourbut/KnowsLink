# 실제 일정 API 연동 제품 범위 — SAR-SCHEDULE-001

## 상태와 적용 범위

2026-10-20 사용자 결정 D008로 실제 일정 API 연동을 진행한다. 이 문서는 사용자 결정 전의 제품 범위 초안이다. 아래 결정 목록(SD-01–SD-06)에 사용자 답이 기록되기 전에는 DEV에 인계하지 않는다.

현재 제품은 `schedule.query`·`schedule.commit`을 서명·전달하고 owner 승인 게이트를 거친다. 승인 뒤에도 실제 캘린더 조회·일정 생성은 실행하지 않는다. 근거는 [D02 MVP](SAR-MVP.md)의 MVP-08/11·DEC-02, [D03](../../design-docs/architecture.md)의 gate-consume 효과·공개 false, [U5](../../design-docs/SAR-UX-ISSUES-002.md#u5--사람이-판단하는-승인-요약)의 고정 문구다. 이 문서는 [백로그 DEC-02](../SAR-MVP-backlog.md#미정-결정과-재개-조건)를 닫기 위한 제품 근거다. 사용자 결정 뒤 SAR-MVP-003의 재개 조건이 된다.

[사람 친구 D02](SAR-HUMAN-PEER.md)의 HP-01–16은 유지한다. 특히 HP-15에 따라 친구 수락은 대화 경로 동의일 뿐이다. 친구 수락만으로 일정 정보를 공개하지 않는다. 기술 구조·API·저장 방식·라이브러리는 DEV가 정한다. 외부 API 근거와 선택지 비교의 원문은 [결정 근거 보고](../../evaluations/qa-reports/SAR-SCHEDULE-001-DESIGN/report.md)에 있다.

## 용어

- 캘린더 연결: 회원이 자기 Google 계정의 캘린더 접근을 KnowsLink에 별도로 동의한 상태다. 로그인 동의와 구분한다.
- 조회 요청: 친구의 agent가 보낸 `schedule.query`다. 시간 범위(window)와 단위(granularity_min)만 담는다.
- 바쁨 구간: 캘린더 제공자가 돌려준 바쁜 시간의 시작·끝이다. 제목·참석자·위치·설명을 포함하지 않는다.
- 응답 대상자: 조회 요청을 받은 회원(B)이다. 일정 정보의 소유자다.

## 사용자 결정 목록

coor는 아래 순서로 사용자에게 묻는다. 각 항목의 첫 선택지가 designer 추천이다. SD-01과 SD-02는 나머지 항목의 전제다.

### SD-01 대상 캘린더

| 선택지 | 영향 |
|---|---|
| A. Google Calendar만 (추천) | 현재 로그인 수단이 Google이다. 같은 계정에 증분 동의로 연결한다. Google의 빈 시간 조회 응답에는 제목 필드가 없다. |
| B. Google + Microsoft Outlook | Microsoft 앱 등록·동의가 추가된다. Microsoft의 빈 시간 조회(getSchedule)는 개인 계정을 지원하지 않는다. 응답에 제목·위치가 들어올 수 있어 서버가 걸러야 한다. 개발·QA 범위가 약 2배다. |
| C. Google + Outlook + iCloud | iCloud 서드파티 연결은 앱 암호를 쓸 수 있다. 공식 개발자 API 경로는 확인하지 못했다. 비밀번호급 자격을 받는 화면이 생길 수 있다. 추천하지 않는다. |

### SD-02 조회 실행 위치

| 선택지 | 영향 |
|---|---|
| A. KnowsLink 서버가 연결 토큰을 보관하고 조회한다 (추천) | 받는 사람의 agent 종류와 무관하게 동작한다. 서버가 반환 필드를 바쁨 구간으로 강제한다. 서버가 refresh token을 암호화 보관해야 한다. 서버 유출 때 영향이 커진다. |
| B. 받는 사람의 agent가 자기 캘린더 도구로 조회한다 | KnowsLink는 토큰을 보관하지 않는다. 결과 형식만 검사한다. Grok·Dots 등 각 agent의 캘린더 도구 지원이 확인되지 않았다. agent가 제목을 섞어 보내도 형식 검사 외에는 막기 어렵다. |

| 선택지 | 영향 |

| C. 친구 수락만으로 자동 조회 | HP-15와 C4 기본 비공개에 어긋난다. 선택하지 않는다. |

## 추천안 기준 제품 규칙 초안

이 절은 SD-01–06의 추천(A)을 전제로 한다. 사용자가 다른 선택지를 고르면 해당 규칙을 다시 쓴다.

### 사용자 흐름

1. B는 내 계정에서 '캘린더 연결'을 누른다. Google 동의 화면에서 빈 시간 조회 권한만 허용한다.
2. KnowsLink는 연결 상태를 '연결됨 — 바쁜 시간만 확인합니다'로 표시한다.
3. A의 agent가 친구 B의 agent에게 `schedule.query`를 보낸다. 서버는 기존 서명·친구 관계·현재 권한을 확인한다.
4. B의 승인 목록에 요청이 나타난다. 요약은 '누가', '확인하려는 기간', '단위', '공개되는 내용: 바쁜 시간대만'을 보인다.
5. B가 '이 요청 승인'을 누른다. 서버는 그 요청 하나에 대해 한 번 조회한다.
6. 서버는 바쁨 구간을 단위로 반올림해 A에게 결과로 보낸다. 결과에는 허용 필드만 있다.
7. B가 거절하거나 기한이 지나면 A는 `denied`를 받는다. 조회는 실행하지 않는다.

### 화면 문구 원칙

- 연결 전 안내: '친구가 요청하고 내가 승인할 때만, 해당 기간의 바쁜 시간대를 알려 줍니다. 일정 제목·참석자·장소는 공유하지 않습니다.'
- 승인 직전 고정 설명은 캘린더 연결 회원에게 '승인하면 이 요청의 기간에 대해 바쁜 시간대만 한 번 공유합니다. 일정을 만들거나 바꾸지 않습니다.'로 바꾼다. 캘린더 미연결 회원과 `schedule.commit`에는 U5의 기존 문구를 유지한다.
- 미연결 회원의 조회 요청 상세: '캘린더가 연결되지 않아 이 요청에 답할 수 없습니다.'와 '캘린더 연결' 링크를 보인다. 승인 버튼은 그리지 않는다.
- 결과를 받은 쪽은 '바쁨' 구간과 '정보 없음'을 구분한다. 바쁨이 없는 구간을 '확정 가능'으로 표현하지 않는다.
- AI 요약·hint·대화 text를 공개 범위로 승격하지 않는다. U5 규칙을 그대로 따른다.

### 실패·만료·철회

| 상황 | 규칙 |
|---|---|
| 캘린더 미연결 | 승인할 수 없다. A에게 `denied`를 보낸다. 사유는 '상대가 응답할 수 없음'까지만 알린다. 미연결 사실을 따로 공개하지 않는다. |
| 회원이 연결 해제 | 즉시 KnowsLink의 토큰을 폐기한다. 제공자 쪽 권한 철회도 요청한다. 대기 중 요청의 승인은 조회를 실행하지 않고 `denied`로 끝난다. |
| 제공자 쪽에서 권한 철회·토큰 만료 | 다음 조회가 실패하면 연결 상태를 '다시 연결 필요'로 바꾼다. 해당 요청은 `failed`다. 자동 재요청 동의 화면을 띄우지 않는다. |
| 친구 해제·차단 | HP-13/14를 따른다. 승인된 요청도 조회·결과 공개를 하지 않는다. |
| 제공자 일시 오류·한도 초과 | 승인한 요청 하나에 대해서만 짧게 재시도한다. 승인 기한 안에서 끝나지 않으면 `failed`다. 새 승인 없이 다른 요청에 재사용하지 않는다. |
| 같은 승인 중복 제출 | 조회는 최대 한 번이다. 결과도 한 번만 보낸다. |

### 기록과 보존

- 감사 기록은 요청 ID·요청자·응답자·기간·단위·결정·결과 상태·시각만 남긴다. 바쁨 구간 원본과 토큰은 감사 기록에 넣지 않는다.
- 결과 원문은 기존 업무 R의 짧은 보존을 따른다. 대화 24h 보존을 일정 결과로 확장하지 않는다.
- 토큰은 서버에만 둔다. 화면·로그·agent·친구에게 보이지 않는다.

| SC-05 실패 구분 | 미연결·재연결 필요·제공자 오류·한도 초과가 `denied` 또는 `failed`로 구분된다. 실패를 `done`으로 표시하지 않는다. |
| SC-06 철회 | 연결 해제·친구 해제·차단 직후의 승인과 대기 요청이 조회하지 않는다. |
| SC-07 문구 | 승인 화면과 연결 화면에 위 고정 문구가 있다. 미연결 회원에게 승인 버튼이 없다. |

### 범위 밖

- 일정 생성·수정·삭제와 초대 발송(SD-03 B/C 선택 전까지).
- Outlook·iCloud 등 다른 캘린더(SD-01 B/C 선택 전까지).
- 친구별 자동 허용과 승인 없는 silent 조회(SD-05 B 후속).
- 제목·참석자·위치 공유, 여러 캘린더 선택, 다른 Google 계정 연결.
- 결제·상품 한도와의 연결. Free N·가격은 DEC-01에 남는다.

## 운영·심사 영향

Google 공식 문서는 캘린더 일정 읽기를 sensitive 권한의 예로 든다. 캘린더 권한은 restricted 목록에 없다. 빈 시간 조회 전용 권한(`calendar.freebusy`)의 분류는 문서에 없으며 Cloud Console에서 확인해야 한다. sensitive이면 앱 심사 전에 미확인 앱 경고와 신규 사용자 누적 100명 상한이 적용된다. 앱이 Testing 상태이면 refresh token이 7일 뒤 만료되므로 상시 연결 출시에 쓸 수 없다. 세부 분류·한도·출처는 [결정 근거 보고](../../evaluations/qa-reports/SAR-SCHEDULE-001-DESIGN/report.md#외부-api-근거)를 따른다. 심사 신청·콘솔 설정은 coor·ops가 사용자 승인 뒤 수행한다. 이 문서는 심사를 신청하지 않는다.
