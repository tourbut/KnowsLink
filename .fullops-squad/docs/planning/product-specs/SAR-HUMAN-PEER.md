# KnowsLink 사람 중심 연결과 대화 제품 기준

## 공개 소개와 로그인 시작 — SAR-LANDING-GUIDE-001

2026-10-14 사용자 요청에 따라 첫페이지에 서비스 소개·설치·사용 순서·사용예시를 제공한다. 실제 회원 기능은 로그인해야 사용한다. 최신 요청은 D04의 이전 최소 로그인 문구 지시를 공개 안내 범위에서 대체한다. HP-01–16의 친구·agent·권한·발송 승인·기한은 바꾸지 않는다. 과거 원천과 수락·실패·미실행 기록은 보존한다.

이 절은 설계 기준이며 아직 새 페이지의 구현·운영 수락이 아니다. [D04 공개 첫페이지](../../design-docs/mockups/service-member-ui.md#공개-첫페이지-정본--sar-landing-guide-001)가 화면·한국어 카피·상태·토큰의 유일한 정본이다. [D11](../../operations/user-guide.md)의 새 안내 절과 연결한다.

| ID | 제품 결정 | 관찰 가능한 완료 조건 |
|---|---|---|
| LG-01 공개 안내 | `/`에서 서비스 목적·시작 순서·설치·예시·로그인 시작을 로그인 없이 읽는다. | 익명 방문자가 회원·친구·본문·키를 받지 않고 다섯 구획을 읽는다. 읽기·접기·앵커는 로그인이나 발송을 실행하지 않는다. |
| LG-02 회원 재방문 | 로그인한 사람도 `/`에서 안내를 읽고 '대화로 이동'으로 `/home`에 들어간다. | 기존 `/`의 자동 홈 redirect를 의도적으로 바꾼다. 회원의 내 계정에서 서비스 안내로 돌아온다. 이름 미설정은 기존 절차로 이어진다. |
| LG-03 시작 순서 | 로그인·이름, 내 agent 연결, 친구 코드 요청·상호 수락, 대상 선택·발송 순서다. | 현재·향후 활성 agent 공유 범위와 기존 회원의 자기 agent 연결 동의를 설명한다. 웹 설치 불필요를 agent 없이 송신 가능으로 표현하지 않는다. |

| LG-05 사실적인 예시 | 일반 text로 웹 직접 작성과 연결한 agent 발송 요청을 설명한다. | 가상 예시·작성 주체·선행 연결/친구 수락·발송 승인을 보인다. 실회원 대화·일정 API·자동 예약·첨부·자동답장을 꾸미지 않는다. |
| LG-06 수신과 보존 | 수신·화면 알림·답장, 대기·전달됨·읽음을 구분한다. | Grok 실행 process/routine과 Dots Events/구독/표시 지시 조건을 설명한다. 180초 큐·최대24h 웹 사본과 외부 사본 한계를 정확히 쓴다. |
| LG-07 로그인 상태 | 활성 로그인 수단만 표시하고 기존 인증·오류·복귀 경계를 유지한다. | Google-only/both/email-only/none/error/expired/authed를 구분한다. 폼은 한 곳이고 POST/CSRF/CSP·Remote 동의·연결 복귀를 보존한다. 안내에 개인정보를 넣지 않는다. |
| LG-08 사용성과 수락 | 기존 토큰으로 1440/390/320, 키보드와200% 확대에 대응한다. | DEV 필수 검사, tester 독립 동작, designer 실제 시각, 별도 세션 fixed SHA 리뷰가 있다. 정적 설계·과거 PASS를 새 수락으로 사용하지 않는다. |

우선순위 P0는 LG-01–08의 최소 완결 안내와 로그인 흐름이다. 별도 홍보 사이트·가격·상품·공개 회원 검색·다크모드·설치 자동화·클라이언트 다운로드 호스팅은 추가하지 않는다. 설치 메뉴·Events의 계정별 지원은 보장하지 않는다. 공개 페이지에는 내부 모델·SHA·시험 결과·미검증 운영 이력을 홍보 내용으로 노출하지 않는다.

DEV는 화면 동작에 필요한 기술 계획·API/handler·테스트와 D10 영향을 결정한다. 이 제품 설계에서는 D10을 수정하지 않는다. 설계 후속 역할도 codex/gpt-6-astra/high를 유지한다. coor가 문서 고정 리뷰/main 통합 뒤 DEV, tester, 실제 시각 검수와 구현 리뷰를 배정한다. 운영 배포와 실제 계정 송수신은 이 설계 완료에 포함하지 않는다.

## 결정 근거와 적용 순서

2026-10-12 사용자는 실제 자기 이메일 아래 에이전트를 등록하고 이름을 정하도록 요청했다. 친구는 사람 사이에 등록한다. 서로 친구가 되면 그 아래 에이전트가 연결되어 대화한다. 후속 요청은 frontend-design을 사용한 UI/UX 전면 개편이다. 원문 전문은 SAR-HUMAN-PEER-001 역할 아카이브에 보존한다.

이 문서는 현재 사람·이름·친구·대화·이행의 D02 정본이다. 이 범위에서는 SAR-PUBLIC-SERVICE의 PS-05/07/08/14와 이전 agent contacts·대화 composer 금지를 대체한다. 기존 신원·세션·키·전달·인간 게이트 규칙은 아래 변경표에 명시한 부분 외에는 유지한다. 화면 정본은 [D04](../../design-docs/mockups/service-member-ui.md)다. 구현·운영 수락은 아직 없다.

| 이전 잠금 | 새 결정 | 유지하는 경계 |
|---|---|---|
| Contacts=agents, 사람은 owner로만 존재 | 연락처는 사람이다. 친구 수락은 양쪽의 현재·향후 활성 에이전트 연결에 대한 동의다. | agentID·키·자격·실행 주체는 계속 분리한다. |
| 에이전트 쌍마다 첫 초대·수락 | 사람끼리 한 번 요청·수락한다. 이후 에이전트별 관계 등록은 요구하지 않는다. | 서로 다른 사람 사이에는 명시적 수락 전 전달을 금지한다. |
| 장기 채팅 이력 없음, composer 없음 | 짧은 대화 목록·본문·composer를 제공한다. 새 대화 원문은 수락 시점부터 최대 24시간 보존한다. | 무기한 아카이브·검색·내보내기·첨부는 제공하지 않는다. 큐 TTL과 보존은 별개다. |
| text는 연결 시험용, 완료/만료 뒤 원문 삭제 | 새 제품 대화 text는 24시간 이내 읽을 수 있다. 기존 메시지 원문을 복원하거나 보존 기간을 소급 연장하지 않는다. | 기존 signed text v1과 업무 relay.v1을 혼합하지 않는다. |
| pair 권한과 새 세대 | 친구 권한에도 현재 상태와 새 세대를 적용한다. | 철회·차단 뒤 옛 승인·receipt·실행 claim을 재사용하지 않는다. |

## 용어와 신원

- 회원은 검증된 로그인 신원에 연결된 사람이다. 사용자 화면에서는 '나', '친구'로 부른다. peer는 내부 설명에만 쓴다.
- 실제 자기 Google 계정으로 로그인한다. Google issuer/sub와 검증 이메일의 기존 결속을 유지한다. 동일 이메일 문자열만으로 다른 발급자의 계정을 합치지 않는다.
- 회원 이름과 에이전트 이름은 각각 앞뒤 공백 제거 후 1–40 Unicode 문자다. 빈 값·제어 문자·양방향 제어 문자를 거부한다. 일반 텍스트로 출력한다. 이름은 인증 증명이 아니다.
- 이름은 언제든 본인이 바꾼다. 변경은 ID·소유권·키·친구·과거 메시지의 실제 발신 주체를 바꾸지 않는다. 친구는 상대 이름을 수정하지 못한다.
- 중복 이름은 허용한다. 목록과 선택기는 '이름 / 클라이언트 / 구분값'으로 구분한다. 구분값은 비밀이 아닌 짧은 안정 식별자다. 전체 ID는 상세에만 둔다.
- 새 로그인은 회원 이름 설정 후 대화 홈으로 간다. 기존 회원은 이름 설정만 추가한다. 이메일은 자기 계정 화면에서만 마스킹해 보인다. 친구에게는 이메일·Google subject·회원 내부 ID를 공개하지 않는다.

| HP-13 해제·차단 | 어느 쪽이든 친구를 해제한다. 해제는 즉시 새 목록 조회·enqueue·lease·ACK·claim·승인 consume·result 공개를 막는다. 본인이 이미 참여한 과거 대화 복사본만 잔여 보존 기간 읽는다. | 열린 composer에서 해제 뒤 보내도 거부한다. 옛 세대 queued/leased 메시지와 gate는 성공으로 끝나지 않는다. 과거 복사본은 읽기 전용이며 상대의 현재 agent·프로필을 새로 조회하지 않는다. |
| HP-14 차단/재수락 | 차단은 해제와 함께 양방향 새 요청/전달을 막는다. 차단 해제는 차단자만 한다. 해제만으로 친구를 복구하지 않는다. | 상대에게 차단 여부를 공개하지 않는다. 해제/거절/만료 뒤 수동 재요청·새 수락은 새 세대다. 차단 중 옛 pair로 우회하지 못한다. |
| HP-15 승인과 안전 | 친구 동의는 대화 경로 동의다. 결제·삭제·권한 부여·다른 채널 외부 발송·약속의 포괄 승인이 아니다. 메시지의 HTML·명령·링크는 실행/자동 열기 하지 않는다. | 기존 C1–C5, owner gate, 현재 key/member 인가, CSRF, CSP, rate, 출력 allowlist와 deny-by-default가 유지된다. GET으로 수락/발송/승인하지 않는다. |
| HP-16 실제 완료 | 이름 등록, 친구 요청/수락, 친구 agent 노출, 양방향 대화, 해제 뒤 신규 전달 차단이 같은 고정 후보에서 동작한다. | DEV 검사, 독립 QA, designer 직접 시각 검수, 별도 세션 fixed-SHA 리뷰가 있어야 제품 수락한다. 문서/정적 fixture는 기능 수락이 아니다. |

### 거절·취소·해제·차단의 차이

거절은 받은 요청만 끝낸다. 취소는 보낸 요청만 끝낸다. 해제는 현재 친구를 끝낸다. 차단은 친구를 끝내고 향후 요청도 막는다. 거절·취소·해제 후에는 수동 새 요청이 가능하다. 차단 중에는 불가능하다. 이 의미를 같은 버튼 아래 함께 노출하지 않는다.

### 대화의 연속성과 과거 열람 경계

새 대화는 한 번의 시험 요청과 한 번의 관련 답장으로 끝나지 않는다. 각 발송은 독립 메시지이며 각 수락 시각부터 최대 180s의 전달 기한을 갖는다. 현재 친구·agent 권한이 유효하면 앞선 메시지의 전달 기한이 지난 뒤에도 새 메시지를 보낼 수 있다. 각 메시지의 최대 24h 보존 시각도 독립적이다. 답장 표시나 대화 묶음은 과거 승인·lease·실행 claim을 재사용하는 근거가 아니다. 기존 signed text의 단일 관련 답장 계약을 변경하거나 새 경로와 구분하는 기술 방법은 DEV가 정하고 호환 경계를 문서화한다.

과거 대화의 읽기 전용 예외는 현재 활성 회원의 유효 세션과 그 회원이 참여한 메시지에만 적용한다. 철회된 키·만료 세션·비활성 회원·제삼자에게 새 열람권을 주지 않는다. agent 수신 API는 현재 유효 키와 전달 권한을 계속 요구한다. 해제 뒤 열람은 이미 참여한 메시지의 저장된 발신자·수신자 표시를 사용한다. 상대의 최신 프로필·새 agent·새 메시지를 조회하지 않는다. 이름 변경 뒤에도 당시 작성자와 안정 식별자 결속을 보존한다. 대화 본문을 연결 승인·업무 gate의 검증 원문으로 승격하지 않는다.

친구 코드는 본인이 공유하거나 교체할 수 있다. 교체는 새 요청 발견만 막으며 기존 친구·이미 받은 요청을 자동 취소하지 않는다. 코드의 추측 방지 강도·저장 방법은 DEV 책임이다. 응답·오류·한도 안내로 코드 대상의 존재나 차단 여부를 구분하지 않도록 검증한다.

### 용량과 남용 방어

회원당 활성 agent 5개, agent당 활성 키 3개, 회원 100명/agent 200개, 기존 HTTP·queue·gate·receipt·연결 한도는 유지한다. 상품 Free N·가격은 결정하지 않는다.

새 사람 친구 한도는 전체 active 400개, 회원당 active 20명, 전체 pending 200개, 회원당 보낸 pending 10개와 받은 pending 10개다. pending 수명은 24h다. 반복/반대 요청은 한 pending만 사용한다. 기존 agent pair 400개 한도는 보존 중인 legacy pair에만 적용한다. 사람 친구 한도를 agent 쌍의 수로 곱하지 않는다. DEV는 보존 기록과 차단 목록에도 유한한 자원 보호를 설계하고 포화 시 신규만 안전 거절한다. 차단 해제·거절·취소·철회·해제·로그아웃에는 기존 안전 정리 budget을 적용한다. 실패·중복도 기존 rate에 집계한다.

대화 원문 저장도 기존 24h 메시지 20000건과 text 4096 bytes 한도를 공유한다. 별도 무제한 사본을 만들지 않는다. 열람은 owner와 참여 endpoint에 결속한다. 백업은 기존 암호화·접근제한·최대 7일 보관을 유지한다. 대화의 24h 뒤 사라짐은 백업/클라이언트 사본 영구 삭제 약속이 아니다. 이 한계는 대화의 '보존 안내'에서 설명한다. 로그/진단/캡처에 원문·실제 이메일·키를 넣지 않는다.

## 우선순위와 인계

P0는 HP-01–16 전체의 최소 완결 흐름과 안전한 legacy 이행이다. 이름과 CSS만 먼저 배포해 전면 개편 완료로 표시하지 않는다. 사용자 계정·외부 상대·운영 배포는 별도 실행이며 새 외부 발송을 임의 수행하지 않는다.

DEV는 짧은 기술 계획, 전체 구현, 핵심 경계와 필수 회귀, D03/D05/D06/D07/D08/D09/D10 및 README/adapter 안내를 한 과제에서 끝낸다. tester는 고정 구현 SHA 뒤 격리된 회원 A/B/C와 legacy DB를 사용한다. designer는 같은 SHA의 실제 구현 화면을 직접 판정한다. coor는 문서 독립 검토·main 통합 뒤 DEV를 배정하고 전체 수락을 조정한다.

다크 모드·전역 검색·공개 프로필·첨부·장기 보관·읽음 표시·에이전트별 공유 토글·상품/결제는 이번 범위에서 생략한다. 기술 구조·API·DB·웹 발송 권한의 구체적 구현은 DEV 책임이다. 실 Google 로그인·노우/다닷 실제 플랫폼 왕복·운영 이행은 아직 미검증이다.
