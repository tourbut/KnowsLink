# SAR-DB-WAIT-001 DEV 측정과 검증

## 결론

- 개선 1·2·3을 모두 구현했다. 코드 기준 SHA는 `bcd79203ec00e460e515f3e724df1ca26813f3cb`다.
- 개선 3 판정은 통과다. 메시지 1,000건 단일 클라이언트 p50은 현재의 0.40배(52.4에서 20.7 ms)이고, 16 클라이언트 처리량은 1.90배(19.4에서 36.9 tx/s)다.
- 개선 2는 처리량을 올리지 않았다. 꼬리 지연과 `/healthz` 보장이 효과이므로 유지한다. 근거는 아래 "개선 2 판단"에 적었다.

## 복원 경로

`beta.sh`는 내부에서 `docker rm -f`를 호출하고 `shell_guard`가 이를 막으므로 직접 실행하지 않았다. 우회하지 않고 같은 이미지와 `pg_dump -Fc`, `pg_restore`, `beta.sh`에서 꺼낸 같은 SELECT를 `--rm` 컨테이너에서 실행했다. 대상은 합성 측정 DB다. `beta.sh`의 `--network none` 대신 migrate 실행을 위해 격리 Docker 네트워크를 썼다. `bash -n`은 통과했다.

- 구 dump 복원 뒤 Up: `state_type=json human_model=1`, lz4, `same_content=true`(`data::text`와 `state::jsonb::text`의 md5), goose 3, 낮추는 쓰기 거부

`scripts/verify_runtime.py`는 Compose 기동, migration, `json|l` 단언, health, 설정 누락, DB 실패, Tunnel 비활성까지 통과했다. 마지막 adapter 단계만 Windows `subprocess`가 `npm`을 찾지 못해 종료코드 1로 끝났다(이 과제가 바꾸지 않은 줄이다). 같은 명령을 `npm.cmd`로 실행해 `"state":"unconfigured"`를 확인했다. 로컬 Node는 24.13.0이고 프로젝트 기준 22가 아니다. ## 개선 3의 비용

- 행 크기: 100건 7,817에서 8,756, 1,000건 42,286에서 45,204, 10,000건 387,586에서 412,047 byte(6~12% 증가).
- 단일 클라이언트 p95는 줄지 않았다: 100건 18.1에서 22.0 ms, 1,000건 56.3에서 57.4 ms. p50만 줄었다. 원인은 확인하지 않았다.
- `json`은 `\u0000`을 받으므로 `encodedNUL`로 기존 거부를 유지했다. 기존 행에는 jsonb가 NUL을 막아 해당 값이 없다.
- 구 코드 복귀가 불가능하다. 절차와 제약은 [D12](../../../operations/ops-guide.md#sar-db-wait-001-저장-형식-이행-운영-미적용)에 적었다.

## 한계와 못 한 것
